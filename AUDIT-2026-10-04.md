## 1. CRITICAL — the secret store is full of ordinary words, and masking them blinds the agent

### 1.1 The vault stores plain dictionary words as "secrets"

`~/.kvindocode/secrets.vault.json` right now: **133 entries, every one auto-created and named `audited-*`** — 39
are 12 characters or shorter, 26 are 300 characters or longer (up to 2608 — whole file dumps) — plus **83 leak
records** and **188 SHA-256 exclusions**. No human put anything in it.

Hashing candidate words against the stored `sha256` values proves the store holds ordinary text:

| stored value | len | sha256[:12] | entry name |
|---|---|---|---|
| `password` (an ordinary English word) | 8 | `5e884898da28` | `audited-%[ $password$ ]%-5e884898da28` |
| `quoted` (an ordinary English word) | 6 | `b3a2bd470cb2` | `audited-quoted-b3a2bd470cb2` |

Both are words that occur in **this repository's own sources**. They were stored because:

* `DeterministicSecretDetector.IsPlausibleSecretValue` (`src/KvindoCode.Core/Secrets/DeterministicSecretDetector.cs:150-163`)
  rejects a plain identifier only when it contains no digit (`:161`), and only below 8 characters (`:153`);
* the assignment rule is driven by a key-name list (`StrongKeyWords`, `:76-79`) containing
  `secret|token|api[_-]?key|password|passwd|…`, so `foo_secret = <anything with a digit>` becomes a secret; and
* the **outbound** path has no human gate: `AuditingLlmClient.cs:83` calls `_vault.Set(...)` *and*
  `RecordLeak(...)` directly. The confirmation dialog guards only the local model's second opinion
  (`AgentSession.ConfirmAsync`), never the deterministic detector.

46 further entries carry a marker fragment in their tag/type, and many of the 344–2608-char entries are whole
outputs, so the list is mostly noise: a real credential would be impossible to find in it.

### 1.2 Because `RedactionTargets` only skips values of 6 characters or less, those words are masked everywhere

`SecretVault.RedactionTargets` (`src/KvindoCode.Core/Secrets/SecretVault.cs:422-431`) keeps every value longer than
6 characters, so the 8-letter word is a masking target. Consequences, all live:

* **`Read` returns text that is not the file's text.** `ReadTool` runs `SecretPlaceholders.Protect` on every
  line (`src/KvindoCode.Core/Tools/FileTools.cs:205`). A file containing that word is shown to the model as a
  marker with the entry's hash in it. This is happening in this very audit: reading
  `DeterministicSecretDetector.cs` through the app returns a different string than the one on disk.
* **The transcript and every outbound request are rewritten** by the same replacement:
  `AgentSession.Mask`/`MaskToolCalls` (`src/KvindoCode.Core/Agent/AgentSession.cs:713-775`) and
  `AuditingLlmClient.ProtectRequest` (`src/KvindoCode.Core/Llm/AuditingLlmClient.cs:186-198`).
* **`Edit` then cannot work**: the text the model was given is not in the file, so `old_string` never matches.
* The reverse direction is just as bad: a **marker typed into a Bash command is expanded into the plaintext
  value before bash sees the command** (`BashTool.cs:34-38`), so a command can silently contain a value the
  model never wrote. I hit that while writing this report.

### 1.3 The masking has already written vault markers into this repository (verified on disk)

`src/KvindoCode.Core/Secrets/DeterministicSecretDetector.cs:219` — an ordinary code comment — now literally
contains a vault marker (the `audited-token-96fd795dc663` entry) where a URL template
`https://user:%[ $CI_TOKEN$ ]%@host` used to be. `src/KvindoCode.Core/Secrets/SecretPlaceholders.cs` keeps two
markers in its XML doc the same way. Hex-dumping the file shows the marker bytes on disk:

```
src/KvindoCode.Core/Secrets/DeterministicSecretDetector.cs:219
  68 74 74 70 73 3a 2f 2f 75 73 65 72 3a 25 5b 24   https://user:%[$
```

A `Write`/`Edit` put them there, because a *masked* `Read` is what the model was shown. This is the loop the
first audit predicted (its S4/S11); it is now damaging the project's own sources.

### 1.4 Tool output is silently replaced by an error, freezing the agent (observed twice tonight)

When a masked `Read` is audited, the detector can flag a span that **contains a marker** — which happens
whenever one vault value is a substring of the text `Protect` has just written (e.g. the 8-char entry
`6e9400cdb4c5` inside a freshly written marker). `SecretVault.Create` refuses such a value
(`SecretVault.cs:333`: "A placeholder cannot be stored as a secret value"), the tool-output path calls exactly
that (`AgentSession.cs:304` → `vault.Set(name, value, …)`), and the catch converts the exception into
**discarding the entire tool result** (`AgentSession.cs:1452`):

```
Tool output hidden because secret auditing or vault storage failed:
A placeholder cannot be stored as a secret value; resolve it first.
```

I hit this twice while auditing (reading `DeterministicSecretDetector.cs`, twice in a row); it is also why the
agent goes blind on files it just read. It is deterministic given this vault; a fresh vault does not reproduce
it (verified). `Protect` is also **not idempotent** for such a value: run against the real vault, `Protect`
over that file grew it 20932 → 21406 bytes and produced one span with `markerInside = True` — the
substitution re-creates part of its own input.

### 1.5 There is no way to undo any of it from the app

`SecretShapes.Describe` (`SecretShapes.cs:14-34`) can flag exactly these entries (short, low entropy,
identifier-shaped, >500-char blocks) and `SecretsWindow` lists them — but nothing *bulk* acts on the verdict,
and **0 of the 83 leak records are marked rotated**. The only way from a bad entry to gone is one-by-one, and
the entry to remove often has a mangled marker as its name (`audited-%[ $NAME$ ]%-<sha>`), which the `Secrets`
tool cannot address cleanly.

## 2. HIGH

**H-1. Plan mode can run any command — the read-only gate is bypassable (verified by running it).**
`ReadOnlyCommand.IsSafe` (`src/KvindoCode.Core/Tools/BashTool.cs:154-200`) has `command` in its `Safe` set
(`:142`), so `command rm -rf /tmp/x` → **True**; `env -S'rm -rf /tmp/x'` → **True** as well (`:195` only
requires each argument to start with `-` or contain `=`, and GNU `env -S` then splits and executes it).
`sed -i`, `find -delete` and `xargs` were correctly rejected. Plan mode's promise ("only read-only exploration
is permitted") rests entirely on this predicate (`BashTool.AllowedInPlan`, `:26`).

**H-2. Vault values are spliced into shell text unquoted.** `BashTool.RunAsync` expands markers in the command
*string* before bash sees it (`BashTool.cs:34-38`), with no quoting or escaping, so a stored value containing a
space, `$`, backtick or `$( )` is re-parsed by the shell — word splitting and command substitution on data that
was supposed to be a value.

**H-3. Marker substitution into JSON tool-argument text corrupts the call.**
`AuditingLlmClient.ProtectRequest` (`src/KvindoCode.Core/Llm/AuditingLlmClient.cs:193`) runs
`SecretPlaceholders.Protect` over `ToolCall.Arguments` as **raw JSON text**, so a marker containing `"` or `\`
breaks the JSON sent as the tool call. The read side deliberately avoids this by masking the parsed tree
(`SecretRedactor.RedactJson`, `AgentSession.cs:772`); the write side does not.

**H-4. `SchedulePrompt` can start two turns at once.** `AgentSession.cs:558` `if (!IsRunning) await
RunTurnAsync(...)` is a TOCTOU against the UI's send path; `RunInternalAsync` throws
`InvalidOperationException("A turn is already running.")` (`:1087`) and the schedule loop catches only
`OperationCanceledException` (`:562`), so the tick dies with an unhandled error.

**H-5. A malformed `timeout`/`async` in a hooks file silently disables every hook.** `HookConfig.Load` does raw
`JsonNode` casts (`(int?)h?["timeout"]`, `(bool)a` — `src/KvindoCode.Core/Hooks/Hooks.cs:61`) that throw on
`"timeout": "60"`; the surrounding `catch` is per whole file (`:69`), so one bad entry drops *all* hooks from
`settings.json`, including PreToolUse blockers, with no warning. Same shape in `MiscTools.cs:157` (`(bool)ms`)
and `MiscTools.cs:81` (non-object array items).

**H-6. `MaskToolCalls` parses tool arguments outside a try.** `AgentSession.cs:762`
`JsonNode.Parse(c.Arguments)` — a truncated argument (exactly what `argsMaybeTruncated` exists to tolerate)
throws while masking and escapes the loop; the `catch` at `:773` covers only the second parse.

**H-7. `settings.json` is written from the thread pool with no coordination.** `AgentSession` mutates and saves
the one shared `AppSettings` from the agent thread (`AgentSession.cs:1270` `_settings.ModelTokens[...] =`,
`:1160` `_settings.Save()`), while the UI thread edits and saves the same object; the save is
`catch { }`-swallowed, so a collision silently loses the user's edit.

## 6. Order of work

1. **Stop the store filling up.** Gate the *deterministic* outbound path behind the same confirmation the
   second opinion gets (or an allow-list), and refuse to auto-store a dictionary word, a plain identifier, or
   anything too short to be a credential. This is the root of §1.
2. **Make masking safe.** `Protect` must be idempotent and must never substitute a value that is a substring of
   a marker it is writing; `RedactionTargets` must exclude any value that occurs inside a marker; and the
   tool-output path must not turn "cannot store" into "discard the whole output" (`AgentSession.cs:1452`).
3. **Purge what is there.** The 133 auto-created entries and 83 leak records need one bulk action driven by
   `SecretShapes.Describe`, and marker-named entries must be deletable.
4. **Plan mode and shell.** Fix `ReadOnlyCommand` (`command`, `env -S`, `type`, `xargs`) and quote/escape vault
   expansion in `BashTool`.
5. **The crash list (§3).** `TaskTools.cs:41`, `SecretTools.cs:143`, `Hooks.cs:61`, `AgentSession.cs:558` and `:762`.
6. **The UI pass (§4)** once the tree has a single writer again.
