## 2. STILL OPEN

### 2.1 False-positive detection — unchanged, and still applied on only one of the two paths  ⚠ highest priority
* `IsFalsePositive` (`AuditingLlmClient.cs:153-165`) still rejects only `^[A-Z_][A-Z0-9_]*$` (SCREAMING_CASE),
  32-128-char hex, GUIDs, `${…}`, `$(` and its own marker — **every other token ≥7 chars passes**.
* It is called **only** on the outbound-request path (`:48`). The **tool-output** path
  (`AgentSession.cs:1112-1119`) has **no** such check: `ResolveSecretValue` (whole whitespace-delimited token
  around the auditor's 8-char quote) + `Length > 6`, then store at confidence ≥0.85, ask the user below it.
* Last proof it misfires: the running build created a 12-char entry named `audited-token-<hex>` at **17:18**
  ("detected by the auditor in Bash output") — after every pass-1 fix. It is gone only because the whole vault
  was emptied at 17:55.
* The heuristic is duplicated: `AuditingLlmClient.Resolve` (`:122`) and `AgentSession.ResolveSecretValue`
  (`:123`); only the first filters anything.

### 2.2 No purge / quarantine capability inside the app
`SecretsWindow.cs` still only deletes entries one at a time; grep for `purge|cleanup|false positive` in `src`
→ nothing. The vault is empty today only because it was emptied externally. Without 2.1's fix plus a bulk
action, the same records will come back.

### 2.3 Masking still rewrites what the model reads
`FileTools.cs:157` still calls `SecretPlaceholders.Protect` on **every Read line** (unchanged since 2026-10-02);
`AgentSession.Mask`/`MaskToolCalls` mask every event and tool argument. With 2.1 in place the symptoms will
return as soon as the vault refills.

### 2.4 The outbound audit still inspects only the newest message
`Collect`/`CollectFullText` (`AuditingLlmClient.cs:101-116`) audit `Messages.LastOrDefault(...)` — a secret in an
older message or deeper in a pasted document is never scanned. `AuditImageAsync(image.Data, "image/png")`
(`:56`) still hardcodes PNG for every image.

### 2.5 Silent data loss on unreadable state
`SecretVault.LoadFileOnly` `catch { return new VaultFile(); }` (`SecretVault.cs:188`) and `AppSettings.Load`
`catch { /* defaults */ }` (`Settings.cs:84`): an unreadable file becomes "empty" and the next write overwrites
the real one. **No `.bak` anywhere** (grep `\.bak` in `src` → 0). `AgentSession.cs:932` still saves settings on
every model call. **Note:** the vault losing 41 entries in one step today matches this failure mode — I could
not prove whether it was that or a deliberate manual purge; worth checking.
